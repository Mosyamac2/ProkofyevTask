# План v2: альтернативный подход к проверке покрытия сценариев

> Этот документ — **переосмысление задачи без привязки к стартовой гипотезе** (эмбеддинги + cosine). Он построен поверх разведки данных из `PLAN.md` v1: структура файлов, объёмы, поля и нормализация там же. Здесь — только то, что меняется или добавляется по сравнению с v1.

---

## 0. Переформулировка задачи

Исходная постановка («найти ближайший сценарий по эмбеддингам») — частный случай. Полная формулировка:

> Для каждого реального запроса определить, относится ли он к одному из **N+1 классов**: N сценариев HR-каталога плюс класс «out-of-scope». Целевой объект анализа — именно класс «out-of-scope» и его внутренняя структура.

Это меняет фокус:

| Что было в v1                                    | Что становится в v2                                                             |
| ------------------------------------------------ | -------------------------------------------------------------------------------- |
| Один сигнал (cosine) → бакеты по порогу         | Каскад сигналов с калиброванной вероятностью покрытия                            |
| Однонаправленный анализ (real → scenario)       | Двунаправленный (real → scenario **и** scenario → real)                          |
| Реальный запрос — изолированная строка           | Реальный запрос — реплика в `dialog_id`-контексте                                |
| HR-метаданные (`action_type`, `agent`) — для вывода | Эти же поля — как фичи матчинга и приоры                                      |
| `lt.choisen_agent` — диагностика                | `lt.choisen_agent` — основной «noisy supervisor» для калибровки без ручной разметки |

## 1. Каскадный пайплайн матчинга (дёшево → дорого)

Главное архитектурное решение: **не пытаться решить задачу одним инструментом**. Строим каскад из 4 этапов; каждый следующий вызывается только для того, что не разрешил предыдущий. Это снижает API-стоимость на порядок и улучшает точность.

```
[real query]
   │
   ▼
Stage A. Exact / button match           ──► точно покрыт (score=1.0)
   │
   ▼
Stage B. Lexical (BM25 + char n-gram)   ──► точно покрыт, если BM25-score ≥ T_lex
   │
   ▼
Stage C. Embedding retrieval top-K      ──► top-K кандидатов (не финальный вердикт)
   │
   ▼
Stage D. LLM-судья на top-K (cross-encoder)
                                          ──► финальный класс ∈ {scenario_id, OOS}
                                          + вероятность
```

### Stage A — exact / fuzzy / button match
- Нормализация (NFKC, lower, схлоп пробелов, убрать пунктуацию по краям).
- `exact == scenario_query` или `exact ∈ button_lexicon` (формируется автоматически: реплики, у которых `n_question > 1` и которые в ≥ 80 % случаев следуют сразу за фиксированным ответом агента — это и есть кнопки UI).
- RapidFuzz `partial_ratio ≥ 92` для опечаток.
- Стоимость: ноль API-вызовов. Эмпирически закрывает 30–45 % трафика (топ-20 запросов в логах — все button-like).

### Stage B — лексический матчер (BM25 + character n-gram)
- BM25 поверх `category + scenario_query` — берёт keyword-driven случаи без эмбеддингов.
- Дополнить character n-gram TF-IDF (n=3..5) — устойчив к словоформам и опечаткам в русском.
- Если top-1 BM25-score выше порога **и** top-1 по embedding (см. Stage C) совпадает с ним — высокая уверенность, не нужна Stage D.

### Stage C — эмбеддинги (как в v1, но как retrieval, не как verdict)
- Эмбеддим `category + scenario_query` (как в v1).
- **Дополнительно:** делаем query rewriting для коротких запросов (< 5 слов) через GigaChat chat: «расшифруй намерение пользователя одним предложением». «отпуск» → «вопрос про оформление, остаток или планирование отпуска». Эмбеддим расширенный текст. Эмпирически добавляет 10–15 п. п. recall на коротких репликах.
- Берём **top-K = 5** кандидатов, **никогда** не принимаем решение «по порогу». Эмбеддинг — это retrieval, не классификатор.

### Stage D — LLM-судья (cross-encoder через GigaChat chat)
Для серой зоны (top-1 score эмбеддинга ∈ [0.45, 0.80]) или для запросов с `top1 − top2 < 0.05` запускаем chat-completion:

```
Системный промпт:
  Ты помогаешь HR-аналитику. Реальный запрос пользователя и 5 сценариев
  из каталога. Определи, покрывает ли какой-то сценарий запрос. Учти, что
  «покрывает» означает одинаковое намерение и тип действия, а не просто
  общую тему.

Вход (для одного реального запроса):
  REAL: "..."
  C1: "{category}. {scenario_query}"   (action_type: ...)
  C2: ...
  ...
Ожидаемый JSON-выход:
  {"verdict": "covered"|"partial"|"oos",
   "matched_scenario_id": int|null,
   "confidence": 0..1,
   "reason": "..."}
```

- Это **настоящий cross-encoder**: модель видит обе строки одновременно, а не их независимые векторы.
- Стоимость: ~10–12k серых запросов × ~700 токенов ≈ 8M токенов. На GigaChat Lite — приемлемо для разовой аналитики. На Pro — оправдано только для финального прохода.
- Батчинг: 5 реальных запросов на один chat-вызов (с явной нумерацией) снижает overhead в ~5×.

## 2. Использование скрытой разметки: `lt.choisen_agent`

Это **самая недооценённая колонка** в данных. У нас уже есть 76k размеченных пар (реальный запрос → агент, который его обработал). Применения:

1. **Приор для retrieval.** Если у реального запроса `lt.choisen_agent == agent-analytics`, то сценарии из «Агент Аналитик» получают boost. Реализация: при cosine-ранжировании умножаем score на `(1 + α)` для сценариев правильного агента (α ≈ 0.05–0.10).
2. **Калибровка порогов без ручной разметки.** Метрика «agent-consistency rate»: доля случаев, где предсказанный сценарий принадлежит тому же агенту, что и `lt.choisen_agent`. Для bucket «точно покрыт» эта доля должна быть > 0.9; для «совсем не похоже» — низкая, но не нулевая (oversight оркестратора). Если у v1-порогов consistency не растёт монотонно — пороги/модель плохи.
3. **Negative pairs для обучения.** Все пары (real query, сценарий **не его** агента) — гарантированные негативы. Тысячи бесплатных негативных примеров для калибровки Platt scaling / валидации embedding-модели.
4. **Sanity-check сценарного покрытия.** Если эмбеддинг отправляет запрос в агента X, а реальный оркестратор отправил в Y — это либо ошибка эмбеддинга, либо реальная неоднозначность дизайна каталога. Оба случая ценны для HR.

Важный нюанс: `lt.choisen_agent` сам по себе **шумный** (оркестратор тоже ошибается). Поэтому он именно noisy supervisor, не gold standard.

## 3. Bidirectional-анализ: покрытие + утилизация

В v1 решается только вопрос «что не покрыто». Симметричный вопрос: «что HR придумал, а реально не используется?» — для бизнеса не менее ценен (зомби-сценарии = впустую потраченная разработка).

### 3.1 Forward coverage (как в v1)
- Для каждого реального запроса → ближайший сценарий + класс.
- Метрики: coverage по уникам, coverage по событиям (взвешено на count).

### 3.2 Reverse utilization (новое)
- Для каждого сценария → реальные запросы, которые к нему привязались.
- Метрики: utilization по сценариям (доля сценариев с ≥ 1 матчем), скос по агентам (какие агенты переразработаны, какие — недозаполнены).
- Артефакт: `out/zombie_scenarios.xlsx` — сценарии без единого матча, отсортированы по сложности реализации (есть готовый агент? есть виджет?). Это **прямой ROI**-вопрос для HR.

### 3.3 Sequential overlap матрица
- Таблица `agent × category`: сколько реальных запросов идёт vs сколько сценариев придумано. Видны диспропорции — где каталог «худой», где «жирный».

## 4. Структурное декомпозирование запросов (intent + entities)

Дополнительный (опциональный) сигнал. Для запросов в серой зоне просим LLM выделить:

- **intent**: глагол высокого уровня (получить_информацию / выполнить_действие / получить_помощь / обратная_связь).
- **object**: о чём (отпуск / зарплата / обучение / коллега / собственный_профиль).
- **modifier**: фильтры (по_подразделению / за_период / для_себя / для_команды).

Тот же разбор делается **один раз** для всех 1514 сценариев. Матчинг теперь происходит на уровне тройки `(intent, object, modifier)` — гораздо более устойчиво, чем на тексте.

Стоимость: фиксированный однократный разбор каталога + ~10k LLM-вызовов на серые запросы. **Запасной путь** — включаем только если Stage D даёт нестабильные вердикты.

## 5. Контекст диалога

В v1 каждая реплика — изолированная строка. Это рвёт смысл:

- Строки вида «да», «нет», «Отправить», «Уточнить запрос» бессмысленны в одиночку.
- В `dialog_id` `lt.n_question` упорядочивает реплики; `last_agent_responce` показывает контекст.

Подход:
1. **Группировка по `dialog_id`.** Анализируем «реальный запрос» как пользовательский intent диалога, выраженный в первой реплике (`n_question == 1`) **или** в первой реплике после «свободного ввода» (т. е. не button-match).
2. **Кнопочные реплики** (`n_question > 1` + match с UI-лексиконом) исключаем из «свободного запроса» и обрабатываем отдельно как **сигнал использования сценария**, а не как новый запрос.
3. Это автоматически фильтрует 35–45 % шума «button-trails» и оставляет ~10k подлинно свободных формулировок — куда более информативная выборка для проверки покрытия.

## 6. Калибровка без ручной разметки

В v1 калибровка опиралась на гистограмму + опц. 200 ручных пар. В v2 — три источника бесплатной разметки:

1. **Agent-consistency** (см. §2) — proxy для positive/negative.
2. **Exact-match pairs** — реплика буквально совпадает со сценарием → гарантированный позитив (только для калибровки, не для метрики).
3. **Cross-agent random pairs** — реплика к агенту X vs сценарий агента Y → гарантированный негатив.

На этих парах строим **Platt scaling**: `P(match | cosine) = σ(a·cosine + b)`. Дальше всё ниже `P ≥ 0.7` идёт в Stage D, никакого «порога по cosine».

Ручная разметка (200 пар стратифицированно по бакету `P`) остаётся как **финальная sanity-проверка**, а не как механизм выбора порогов. Это снимает риск «пороги от глаза».

## 7. Сегментные срезы

Где скрыты неоднородности, которые средние метрики прячут:

| Срез              | Гипотеза                                                                     |
| ----------------- | ---------------------------------------------------------------------------- |
| `pd.block`        | Покрытие в HQ ≠ покрытие в территориальных банках; у регионов могут быть свои темы |
| `lt.created_at` (мес) | Появляются ли новые непокрытые темы со временем = поведение реальных юзеров эволюционирует, а каталог нет |
| Длина запроса     | Короткие button-реплики vs длинные свободные запросы — разные распределения покрытия |
| `n_question == 1` vs остальные | Первая реплика диалога ≠ дальнейшие; первая — настоящее намерение |

Артефакт: `out/coverage_segments.xlsx` — coverage rate по всем срезам, с p-value t-теста против общего среднего. HR увидит, где «дыры» концентрируются.

## 8. Расширенные метрики (вместо одного coverage rate)

| Метрика                              | Что измеряет                                                              |
| ------------------------------------ | -------------------------------------------------------------------------- |
| Coverage rate @ event                | Σ count(covered) / Σ count(all) — взвешено на частоту                     |
| Coverage rate @ unique               | |covered uniques| / |all uniques| — без перекоса от хвоста                |
| Hit@K (K=1, 3, 5)                    | Доля случаев, где правильный сценарий в top-K эмбеддингов — качество retrieval-стадии |
| Agent-consistency by bucket          | Калибровочная метрика (см. §2)                                            |
| Utilization rate                     | |scenarios with ≥1 match| / |all scenarios| — зомби-сценарии              |
| Gap concentration (Gini)             | Насколько непокрытые запросы сконцентрированы в нескольких темах          |
| Cluster purity (внутри gap-кластера) | Согласованность кластера — мерится по разнообразию `lt.choisen_agent` внутри кластера |

## 9. Стек и порядок реализации

```
ProkofyevTask/
├── ... (всё из v1)
├── lexical.py          # BM25 + char n-gram (Stage B)
├── llm_judge.py        # GigaChat chat для Stage D и query rewriting
├── intent_parse.py     # опц. структурное декомпозирование (§4)
├── dialog_context.py   # группировка по dialog_id, фильтр кнопок (§5)
├── calibration.py      # Platt scaling по noisy supervisor (§6)
├── reverse_analysis.py # утилизация сценариев (§3.2)
├── segments.py         # сегментные срезы (§7)
└── orchestrate.py      # каскад A→B→C→D
```

Чек-лист (порядок, оптимальный по соотношению ценность/усилие):

1. [ ] §5 dialog_context — фильтрация кнопок: **сразу убирает 35–45 % шума**, прежде чем тратить API.
2. [ ] §1 Stage A + B — exact, fuzzy, BM25: бесплатные, закрывают тривиальные случаи.
3. [ ] v1-эмбеддинги как Stage C — но top-K, не top-1.
4. [ ] §6 калибровка через agent-consistency: формирует пороги без ручной разметки.
5. [ ] §3.2 reverse utilization — отдельный отчёт по зомби-сценариям. Дёшево, важно бизнесу.
6. [ ] §1 Stage D — LLM-судья на серой зоне. Самый дорогой шаг, делается на отфильтрованном объёме.
7. [ ] §7 сегменты — последний шаг, поверх готовых меток.
8. [ ] §4 intent-декомпозирование — **только если Stage D даёт шумные вердикты**.

## 10. Чем v2 принципиально лучше v1

| Проблема v1                                                  | Решение в v2                                                                |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| Один сигнал (cosine) → грубо                                 | Каскад A→B→C→D, каждый этап ловит свой тип матчей                            |
| Cosine путает темы и намерения                               | LLM-судья (Stage D) видит обе строки и оценивает intent, не только тему      |
| Пороги «по глазу»                                            | Калибровка Platt scaling на noisy supervisor (`lt.choisen_agent`)            |
| Кнопочные реплики раздувают «покрытие»                       | Dialog-context фильтр (§5) выводит их в отдельный контур                     |
| Зомби-сценарии не видны                                      | Reverse utilization (§3.2) — отдельный артефакт                              |
| Короткие реплики плохо эмбеддятся                            | Query rewriting через LLM в Stage C                                          |
| Серая зона = «непонятно» (= тупик)                          | Серая зона = триггер для Stage D, который выдаёт финальный вердикт           |
| Средние метрики маскируют неоднородности                     | Сегментный отчёт по `pd.block` / времени / длине запроса                     |
| Нет внешней валидации без ручной разметки                    | Agent-consistency rate работает как proxy gold-стандарт                      |

## 11. Когда v1 всё же достаточно

v2 имеет смысл, если задача не разовая, либо если HR будет принимать на её основе решения о редизайне каталога (а это, судя по постановке, именно тот случай). Если же нужен **быстрый разовый сигнал «есть ли вообще дыры в покрытии»** — v1 даст 80 % ответа за 20 % усилий. Тогда v2 — следующая итерация после первичной проверки.

## 12. Открытые вопросы к v2

1. Какая нагрузка на GigaChat chat допустима по бюджету? От ответа зависит, делаем ли Stage D на полном объёме серых запросов или сэмпле.
2. Есть ли у HR ресурс на разметку 200 пар — даже как финальную sanity-проверку?
3. Достаточен ли горизонт логов (по `lt.created_at`) для сегментного анализа во времени, или нужно дотянуть выгрузку до большего периода?
4. Нужны ли результаты в виде дашборда (Streamlit/Superset), или Excel-артефактов достаточно для HR-аналитика?
