# План: проверка покрытия реальных запросов сотрудников сценариями HR

## 1. Цель

Установить, насколько сценарный каталог B2E, разработанный HR-подразделением (`Сценарии B2E.xlsx`), покрывает фактические запросы сотрудников в системе «Пульс» (`orch_logs_to_2026_05_27.xlsx`).

Для каждого реального запроса находим ближайший по смыслу сценарий через семантический поиск на эмбеддингах GigaChat, рассчитываем cosine-similarity, относим к одной из трёх категорий уверенности и получаем как итог:

1. Перечень реальных запросов, которые **уверенно** покрываются каталогом (валидация дизайна).
2. Перечень запросов в «серой зоне» — потенциально похожи, требуют ручной проверки HR-аналитика.
3. Перечень **непокрытых** запросов («совсем не похоже») — кандидаты на новые сценарии и темы для HR.

Дополнительно — кластеризация непокрытых запросов, чтобы вместо списка из тысяч строк отдать HR несколько связных «тем-пробелов».

## 4. Подготовка данных

### 4.1. Сценарии (`data_loader.load_scenarios`)
1. `pd.read_excel(header=None)` → переименовать колонки.
2. `df[['agent', 'category', 'action_type']] = df[['agent', 'category', 'action_type']].ffill()` — восстановить merged-значения.
3. `df.dropna(subset=['scenario_query'])`.
4. Нормализовать строки (`text_norm.normalize`): NFKC, strip, схлоп пробелов, нижний регистр **только для матчинга**; оригинал сохранить в `scenario_query_raw` для вывода.
5. Сборка текста для эмбеддинга:
   `embed_text = f"{category}. {scenario_query}"`
   — гипотеза: категория добавляет домен, что важно для коротких сценариев («Карьера», «Уведомления»). Этот выбор подтверждается тем, что в задаче явно сказано «пара сценарный запрос — категория потребности».
6. Удалить точные дубли `embed_text`, сохранив маппинг `scenario_id -> исходные строки`.

### 4.2. Реальные запросы (`data_loader.load_real_queries`)
1. `pd.read_excel`, оставить `last_user_question`, `lt.choisen_agent`, `pd.block`, `lt.created_at`.
2. Обрезать текст до 1000 символов (страховка от аномалий).
3. Нормализация (та же `text_norm.normalize`).
4. **Фильтрация мусора:**
   - длина после нормализации < 3 символов;
   - содержит только цифры / знаки препинания / эмодзи;
   - служебные команды (`/start`, `/help`).
5. Дедупликация по нормализованному тексту, агрегируем:
   `count`, `n_unique_users`, `top_agent` (mode of `lt.choisen_agent`), `top_block`, `last_seen`.
6. **Раздельная обработка кнопочных реплик:**
   - Эвристика: реплика встречается как exact-match (после норм.) с одним из значений `scenario_query` ИЛИ с одним из частых «button labels» (составить шорт-лист после первичного прогона).
   - Такие пары помечаем `match_kind='exact'`, score = 1.0, через embedding-поиск не гоняем (экономия квоты).
   - Остальное — `match_kind='semantic'`, идёт в эмбеддинг.

### 4.3. Ожидаемый объём вызовов API

- Сценарии: ≤ 1514 эмбеддингов (× 1 прогон).
- Реальные запросы: 16 300 уникальных − exact-матчи (грубо 30–40 % от объёма частых) ≈ **10–12 тысяч** уникальных вызовов.
- При батче 50–100 строк за запрос — 200–250 HTTP-запросов суммарно.

## 5. Работа с GigaChat embeddings API

### 5.1. Аутентификация
1. `Authorization: Basic <base64(client_id:client_secret)>` (этот ключ хранится в `.env` под `GIGACHAT_AUTH_KEY`).
2. POST `https://ngw.devices.sberbank.ru:9443/api/v2/oauth`
   - `scope`: уточнить у владельца ключа — `GIGACHAT_API_PERS` (физлицо), `GIGACHAT_API_B2B`, `GIGACHAT_API_CORP`. По умолчанию ставим `GIGACHAT_API_CORP` (раз ключ корпоративный) и делаем настраиваемым через env.
   - `RqUID`: random UUIDv4 на запрос.
3. Получить `access_token` (живёт 30 минут) — кешируем в памяти + продлеваем по `expires_at`.

### 5.2. Эмбеддинги
- `POST https://gigachat.devices.sberbank.ru/api/v1/embeddings`
- Body: `{"model": "Embeddings", "input": [text1, text2, ...]}`
  - Альтернатива: `EmbeddingsGigaR` (1024-D, для русского обычно качественнее). Делаем `MODEL_NAME` параметром в `config.py`.
- Лимиты: батч до 100 строк (проверить эмпирически: начнём с 50).
- Возврат: `data[i].embedding` — список float; кастуем в `np.float32`.

### 5.3. Сетевая часть
- SSL: GigaChat использует УЦ Минцифры. Варианты в порядке предпочтения:
  1. Установить сертификат через `certifi.where()` + расширение pem.
  2. Передать путь к корневому сертификату через `verify=path_to_pem`.
  3. **Крайний случай:** `verify=False` + `urllib3.disable_warnings()` — допустимо для разовой аналитики, но залогировать предупреждение.
- Ретраи: `tenacity` (3 попытки, экспон. back-off, ретраить 429/5xx).
- Тайминги: на каждый батч ≈ 0.5–1.5 сек → весь корпус за 3–6 минут.

### 5.4. Кеш эмбеддингов (`embed_cache.py`)
- Ключ: `sha1(norm_text + "::" + model_name)`.
- Хранилище: `cache/embeddings.parquet` (columns: `key`, `text`, `vec`) или `cache/embeddings.npz` + `cache/keys.json`. Parquet проще для инкрементального append.
- При повторном запуске пересчитываем только новые тексты — это критично, потому что калибровка/итерация требуют многократных прогонов matcher без повторных эмбеддингов.

## 6. Семантический матчинг (`matcher.py`)

1. Загрузить матрицы:
   - `S ∈ R^{n_scen × d}` — эмбеддинги сценариев (нормированы L2).
   - `R ∈ R^{n_real × d}` — эмбеддинги реальных запросов (нормированы L2).
2. Cosine sim = `R @ S.T` (раз векторы L2-нормированы — это просто скалярное произведение).
3. Для каждой строки R: `topk_idx = argpartition(-sim_row, K)[:K]`, отсортировать, взять scores.
4. Возврат на каждый реальный запрос:
   - `best_scenario_id`, `best_score`,
   - `top_k = [(scenario_id, score), …]` — по умолчанию K=5,
   - `bucket` (см. ниже),
   - `agent_consistency` = (`best_scenario.agent_norm` ⇄ `lt.choisen_agent`) — отдельный диагностический сигнал.

### 6.1. Бакетизация (предварительные пороги — уточнить калибровкой)

| Bucket               | Условие                                  | Действие                                            |
| -------------------- | ---------------------------------------- | --------------------------------------------------- |
| `точно похоже`       | `best_score ≥ θ_high`                    | Сценарий покрывает запрос                           |
| `непонятно`          | `θ_low ≤ best_score < θ_high`            | Серый список → ручная проверка                      |
| `совсем не похоже`   | `best_score < θ_low`                     | Кандидат на новый сценарий                           |

Начальные значения для GigaChat Embeddings на русском: `θ_high = 0.75`, `θ_low = 0.55`. **Эти числа нельзя оставлять на глаз** — см. раздел 7.

### 6.2. Доп. сигнал — top-1 vs top-2 gap
Если `top1.score − top2.score < 0.03` и оба ниже `θ_high` — реальный запрос «между» сценариями. Отмечаем флагом `ambiguous=True` (для будущей UX-доработки сценариев).

## 7. Калибровка порогов (`calibrate.py`)

### 7.1. Без ручной разметки (быстрый старт)
1. Построить гистограмму `best_score` по всем уникальным реальным запросам.
2. Ожидаемо распределение бимодально: пик «высоких» (≈ 0.8) — кнопки/прямые попадания, пик «низких» (≈ 0.4) — небизнес-запросы. Минимум между модами — кандидат на `θ_low`.
3. Использовать `kneedle` / простую второпроизводную поверх KDE сглаживания, найти точки изгиба.
4. **Sanity-проверка по `lt.choisen_agent`:**
   - В подвыборке, где реальный запрос дошёл до сценарного агента (`p2p`, `analytics`, `app-benefits-agent`, …), top-1 сценарий должен принадлежать тому же агенту → считаем долю «agent-совпадений» по бакетам. У бакета `точно похоже` она должна быть существенно выше, чем у `совсем не похоже`. Если нет — модель/пороги плохи.

### 7.2. С минимальной ручной разметкой (рекомендуемый дополнительный шаг)
1. Sampling: 200 пар (стратифицированный по бакету и по частоте запроса).
2. Аналитик HR размечает каждую пару бинарно («match / no match»).
3. Строим ROC по score → `θ_high` = точка с precision ≥ 0.95, `θ_low` = точка с recall ≥ 0.95.
4. Эту разметку сохраняем в `eval/gold_pairs.csv` для повторных регрессий при смене модели.

### 7.3. Метрики на корпус
- **Coverage rate (по уникальным):** `|точно похоже| / |unique queries|`.
- **Coverage rate (по событиям):** Σ`count` бакета «точно похоже» / Σ`count` всего — отражает «насколько часто пользователь натыкается на покрытое».
- **Gap volume:** Σ`count` бакета «совсем не похоже».
- **Top-N gaps:** N самых частых непокрытых уникальных запросов.
- **Per-agent coverage:** разбивка по `lt.choisen_agent`, чтобы видеть, какие агенты «недокармливают» сценарный каталог.
- **Per-category richness:** сколько уникальных реальных запросов привязалось к каждой `category` сценариев — выявит «жирные» категории и «мёртвые» (которые HR придумал, но реальной нагрузки нет).

## 8. Кластеризация непокрытых запросов (`cluster_gaps.py`)

Чтобы вместо «вот вам 6000 строк» дать HR обозримый список «вот ~30 тем-пробелов»:

1. Берём эмбеддинги только тех уникальных запросов, у которых `bucket == 'совсем не похоже'`.
2. Снизить размерность UMAP (n_components=10, metric='cosine'), затем HDBSCAN (`min_cluster_size = max(5, sqrt(N)/2)`).
3. Для каждого кластера:
   - центроид и его ближайший представитель (медоид) — он же label-кандидат;
   - топ-5 самых частых запросов кластера;
   - суммарный объём (Σ count) — приоритет.
4. Опционально: для каждого кластера попросить GigaChat **назвать тему** одним предложением (отдельный chat-вызов, по 1 на кластер; легко проконтролировать) — это упростит чтение HR-аналитику.

## 10. Открытые вопросы (уточнить до запуска)

1. **GigaChat-ключ:** какой scope (`GIGACHAT_API_PERS`/`B2B`/`CORP`)? Есть ли установленный сертификат МинЦифры на машине?
2. **Модель эмбеддингов:** `Embeddings` (быстрее, дешевле) или `EmbeddingsGigaR` (точнее на русском)? — рекомендую начать с `EmbeddingsGigaR`.
3. **Композиция текста сценария:** только `scenario_query` (col D), `category + scenario_query` (рекомендую), или `agent + category + scenario_query`? Запасной вариант — сделать прогон в двух режимах и сравнить, какой даёт более чистое разделение на гистограмме score.
4. **Кнопочные реплики:** считать ли «Найти ментора», «Отправить» и т. п. валидным сигналом покрытия? Они инициированы UI, а не свободной речью — стоит вывести отдельным разрезом, чтобы не маскировать реальные пробелы.
5. **Объём ручной разметки:** готов ли HR-аналитик разметить ~200 пар для калибровки порогов?
6. **Сроки/инфра:** запуск разовый локально, или нужно положить в Airflow / повторять еженедельно с новыми логами?

## 13. Технические риски и митигации

| Риск                                                              | Митигация                                                                                  |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Эмбеддинги «склеивают» совсем разные смыслы (короткий текст)      | Композиция `category + scenario_query`; сравнение двух режимов на отложенной выборке       |
| Пороги, выбранные на глаз, дают перекошенную картину покрытия     | Калибровка через `lt.choisen_agent`-консистентность + опц. ручная разметка 200 пар         |
| Дубли реального вопроса под разной пунктуацией раздувают вызовы API | Жёсткая нормализация + `sha1`-кеш                                                          |
| Кнопочные реплики маскируют «реальное» покрытие                   | Двухконтурный матчинг: exact-bypass для кнопок, semantic — для свободного ввода            |
| SSL-сертификат Сбера не установлен                                | Поддерживать `GIGACHAT_VERIFY` (path / `false`) в конфиге, понятная ошибка с инструкцией   |
| GigaChat изменит формат ответа / модель устареет                  | Изоляция в `gigachat_client.py`, версия модели — параметр; кеш с ключом, включающим модель |
